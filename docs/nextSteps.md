# Plan

Deliver Epicenter as two independent frontend applications—patient and nurse—using one FastAPI backend and one Supabase source of truth. Build and verify the persistence, authorization, workflow, simulator, and MCP contracts before finalising the colour system, then deploy the two panels to Vercel and the shared backend to Railway.

## Scope

- In: physical patient/nurse frontend split; shared backend contracts; Supabase schema and seed; separate Clerk patient enrollment and administrator-controlled nurse provisioning; patient Singpass registration contract, accepted/rejected outcome, ticket and counter; simplified nurse workflow; controlled full CRUD; nurse-panel simulator; Epicenter, insurance-format, and Power BI MCP work; verification; final visual system; Vercel/Railway deployment.
- Out: automated clinical urgency or identity/e-card verification; direct browser access to privileged Supabase keys; raw SQL in the nurse panel; online learning from live patient documents; live Clinic Assist/NEHR/TPA/payment integration; production-scale patient IAM.

## Action items

- [x] **Split the frontend into two deployable apps.** The patient and nurse routes now live in independent `frontend/patient/` and `frontend/nurse/` Next.js workspaces, while `frontend/shared/` exports only typed data contracts, global design tokens, and safe UI primitives. Each app has its own environment example, validation, package scripts, build output, route tree, and Vercel root; contract and production-build checks verify that neither artifact contains the other panel's routes. Both apps target the same versioned FastAPI API and business rules remain outside the frontends.
- [ ] **Complete the Supabase operational schema and seed.** Extend the current migration beyond the initial patient/questionnaire/document fixtures to cover clinics, appointments, queue tickets, patient-safe outcomes/reasons, staff roles, manual identity/e-card attestations, counters, availability, allocation recommendations/decisions, audit events, configuration versions, simulator snapshots/runs, and soft deletion. Regenerate an idempotent seed containing the existing 300 registrations, 60 questionnaires, and 9 documents plus deterministic appointments, nurses, counters, single tickets, administrative-urgency flags, review cases, and simulator scenarios; apply it to a synthetic Supabase project and verify counts, joins, RLS, grants, and zero false-ready cases.
- [ ] **Replace demo repositories with the shared persistence/backend boundary.** Implement Supabase repository adapters and transactional FastAPI services for registration validation, document/readiness processing, accepted/rejected/under-review outcomes, one-ticket queue lifecycle, counter assignment, staff worklists, CRUD, audit, allocation, and simulation-snapshot reads. Keep server secrets in Railway only, require Clerk identity/role/clinic scope on protected endpoints, and add idempotency plus optimistic-concurrency conflicts for all writes.
- [ ] **Implement separate Clerk patient enrollment and nurse provisioning.** Follow [auth.md](./auth.md): expose public account creation only in the patient panel, never offer a role selector, and map each verified Clerk `sub` to exactly one authorized `patient_accounts` record. Keep the nurse panel sign-in-only; create or invite nurses through an administrator-controlled process and grant access only when the Clerk `sub` maps to an active `staff_accounts` record with the required role and clinic scope. Replace the current session-only `require_staff` check with server-side authorization that returns `403` for patients, unmapped users, disabled staff, and wrong-clinic roles. Prepare judge-specific nurse credentials outside the repository plus unique patient test-email instructions, and test patient signup, nurse sign-in, cross-panel denial, account disablement, audit attribution, and sensitive-action reverification against the deployed applications.
- [ ] **Finish the patient panel.** Implement the Singpass Login/Myinfo adapter contract with a clearly labelled synthetic mode, registration field comparison, document upload/reuse, `accepted`/`rejected`/`under_review` status, curated rejection reason and next action, and one live `Q-*` ticket with assigned counter and refresh/realtime states. Add a questionnaire to registration only when the booked screening or appointment type requires it: select the General Health or Occupational Health form from the appointment, prefill identity/contact fields from consented Myinfo data as read-only, collect only the remaining medical, lifestyle, conditional, and consent answers, and autosave/resume the 10–15-minute flow. Walk-ins complete the same required questionnaire at the nurse-supervised kiosk. An incomplete questionnaire creates an actionable `under_review` state rather than a generic rejection and must never delay nurse-led urgent escalation. Prove that patients cannot see internal review reasons, extraction confidence, audit history, direct identifiers, or other patients.
- [ ] **Implement the simplified nurse task flow.** Make Today the default screen with the oldest actionable ticket and one primary next action; show validated facts compactly, expand only exceptions/evidence, record the nurse-performed red-flag and identity/e-card attestation, then accept, reject-with-reason, or keep under review from the same task page. Preserve the original ticket/waiting age and update routing/counter automatically. Keep the main navigation to Today, Review, Patients, Simulator, and Audit, and measure end-to-end task time, touches, corrections, and errors.
- [ ] **Add intentional nurse-side database CRUD.** Build an allowlisted Patients data browser with search/filter/sort/pagination and create/read/update/delete commands through FastAPI—not a SQL console. Require an authenticated session for reads, fresh Clerk password reverification for sensitive reveals and every mutation, and an explicit commit screen containing action, record, before/after values, and reason. Use recoverable soft delete by default, restrict hard delete, make audit/evidence immutable, and test stale writes, retries, duplicate submits, permissions, and reauthentication expiry.
- [ ] **Build the simulator inside the nurse panel.** Implement a deterministic engine and nurse-only UI that pulls a versioned de-identified Supabase seed/snapshot into isolated simulation state. Cover identical-seed baseline comparison, dynamic allocation with approve/modify/reject/expiry/reversal, known administrative-urgency appointments, and pending/completed manual identity verification. Assert that simulation code cannot write operational tables, never infers clinical urgency, never creates a second ticket, and never resets waiting age.
- [ ] **Deliver the MCP layer with strict separation.** Expose the narrow Epicenter Operations MCP over Streamable HTTP for authorized read/explain and synthetic-simulator tools. Build an Insurance Format Registry MCP that learns each new insurance form only from an approved synthetic or formally de-identified template: it proposes the relevant field schema, extraction mapping, and fixture tests; a maker/checker approves and activates the version; future documents are extracted into a database staging record with source evidence and `pending_review`; and only staff-confirmed facts are promoted by the shared backend into canonical patient, coverage, and eligibility tables. The MCP must never learn online from live patient records, write directly to canonical tables, or decide eligibility. Connect Power BI remote MCP to a de-identified aggregate semantic model behind tenant/licensing/preview gates and retain a normal dashboard fallback. Keep Microsoft Learn in developer tooling, Supabase MCP project-scoped/read-only against non-production data, and reject additional MCPs unless they have a named owner, unique capability, least-privilege tool set, data boundary, tests, and removal criteria.
- [ ] **Pass the backend-complete release gate, then finalise visual design.** Before choosing final colours, require backend unit/contract/security tests, fresh-install migration-versus-`backend/persistence/schema.sql` parity, seed integrity, RLS/advisor review, patient/nurse authorization tests, step-up CRUD tests, simulator invariants, MCP schema/adversarial tests, and complete browser journeys for success/failure/retry/stale states. After that gate, finalise palette, typography, status tokens, responsive compositions, WCAG AA contrast, colour-vision checks, and separate patient/nurse visual QA without changing workflow semantics.
- [ ] **Deploy and verify the complete system.** Create separate Vercel projects for the patient and nurse apps, deploy the shared FastAPI/MCP service and worker to Railway, allowlist both exact Vercel origins, apply Supabase migrations/seed to the intended synthetic environment, configure Clerk and the supported Supabase integration, register the Railway `/mcp` endpoint in Copilot Studio, and configure the Power BI analytics agent separately. Run authenticated smoke tests from both public origins through Railway to Supabase, verify health/restart behavior and audit persistence, then confirm remote Git refs and record rollback instructions.
